# Stage 05 · Animate the cards and verify accessibility

## Agent prompt

Apply a single coherent motion system to the built player boards and methodology. Preserve reading and keyboard flow. Movement should make the photos feel like they land on the paper as the reader scrolls. Test the actual images, the complete set of cards and the most constrained mobile view.

### Motion specification

| Element | Trigger | Effect | Timing |
| --- | --- | --- | --- |
| Featured leader photo | The image decodes and its card is in view. Keep above-the-fold content visible from initial render | Subtle settle from 8px lower with `scale(.985)` to rest. Match the same reserved box | 420ms, `cubic-bezier(.2,.75,.25,1)`; stagger second photo by at most 60ms |
| Other player portrait | Its card crosses roughly 16–20% intersection | Rise by 12–16px, fade from 0.4 to 1 and settle from `scale(.98)`. Use 8–10px travel on touch widths | 380–440ms with the same gentle easing. 0–60ms one-time row stagger |
| Card name | Card entrance | Keep legible from first paint. Optional 3–4px settled transform, with no segmented or typewriter text | 260–300ms. Follows portrait by up to 40ms |
| Paper detail or pointer hover | Independent geometry plane after reveal or fine-pointer interaction | 2px settle or static paper shadow. Keep face and image stroke attached to the same layer | 120–180ms. Do not trigger hover animations on coarse pointers |
| Navigation and disclosure | Activate a control | Visible focus immediately. Show disclosure contents immediately. Use short colour or opacity transitions only where helpful | 120–160ms. Avoid animating content height |
| Methodology illustrations | Optional when entering the viewport | A brief opacity transition on decorative geometry only. Data and value labels start visible | Up to 220ms |

1. Use one shared `IntersectionObserver` and a tested reveal component or helper. Use a modest viewport offset and unobserve a card after its first successful reveal. A long mobile card must still intersect sufficiently. Observe on load, on deep-link entry and after quick scroll without queuing the full board. Leave content visible if the API is absent, initialization fails, the user jumps to an anchor or a card gains keyboard focus. Apply transform and opacity to the media wrapper using CSS keyframes triggered by the observer. Avoid unstable scroll listeners, global animating filters, scroll hijack and perpetual motion. [Intersection Observer API](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API)
2. Honor `prefers-reduced-motion: reduce` for media and motion wrappers, the scroll behavior and view transitions. Skip reveal transforms and timers; render content at rest. Verify changing the OS setting during an open session. CSS and behaviour must degrade to accessible static cards if scripting for motion is unavailable. See [reduced motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion) and [W3C animation guidance](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions).
3. Verify descriptive headings, landmarks, ordered list semantics, accessible name and expanded state for disclosure, readable focus treatment and logically grouped tab order. At 200% zoom and 320 CSS px, there is no reading-order loss or clipped content. Check keyboard-only, touch, and at least one screen-reader or accessibility-tree traversal. The sticky navigation should have a matching scroll offset and never cover focus. Every button has a clear hover, focus and active state, labels remain visible, and important distinctions use text.
4. Use correct `width`, `height`, `aspect-ratio`, `srcset` and `sizes` for local media. Eagerly load the first critical leader and use high priority only for the dominant LCP image when measurement supports it. Lazy-load below-the-fold portraits, use async decode where appropriate, and use width variants instead of shipping masters. Fonts should swap with acceptable fallback metrics. Check local bundle for accidental SVG or external asset requests. See [MDN responsive image attributes](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/img).
5. Target up to 180 KB per normal featured image request and 100 KB per ordinary portrait request at standard card sizes. Initial compressed page transfers including two leader portraits should aim for at most 650 KB under a documented viewport, and the initial main script should aim for at most 150 KB compressed if a JS app is used. On a production preview test with a throttled representative mobile profile, aim for LCP ≤2.5s and CLS ≤0.1 across three runs and report the median or the measured shortfall. Use measured transfers as well as visual checks. Optimize the bottleneck while preserving discernible faces and outlines.
6. If an asset errors, keep the player's name and evidence visible, reserve its media size and record the missing asset. Use the pending visual treatment defined in Stage 01 only in development or review. For final handoff, require all correct photos. Make no live data calls during evaluation.

### Loop and handoff

Test a slow continuous scroll and a fast jump through both groups, then revisit each board with keyboard and reduced motion. Confirm entry effects occur for all 20 cards in the normal-motion pass, evidence stays reachable and image decode causes no shift. Capture evidence at desktop and at mobile widths. Repair any timing, crop, accessibility or performance failure and rerun the affected path. **Pass** when the complete page works with and without motion, all expected actual portraits appear, and the visual and loading budgets have been checked.
