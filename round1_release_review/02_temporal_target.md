# F02 · Enforce information and time boundaries

**End goal** Use a common, auditable forecast target with the same information at assessment and release. Separate pre-ball pressure from retrospective impact and pre-match player forecasting.

```text
Open the F01 outputs and review rr_pressure/pressure.py, models.py, impact.py, forecast.py, challengers.py and split.py. Freeze a dated protocol before examining revised results. Choose the supported match-rate or fixed-episode target based on coverage and comparability, then use it everywhere.

Loop: specify -> build time-ordered features and labels -> mutate future data -> verify.

1. Document the three clocks. Pre-ball state at t uses only earlier events and match facts known at t. Past impact uses the observed event minus a contemporaneous peer reference. Auction scoring uses evidence available at the dated auction forecast cutoff and a declared scenario. Distinguish per-12 legal-ball rate from the outcome of an actual 12-ball episode. A good default is a match pressure-impact rate normalized to 12 among predeclared qualifying opportunities. Observed ball count may define label and evaluation support, with selection bias reported. It must be absent from inputs in both training and backtests. For an actual fixed-window design require genuine valid episodes, explicit censoring when a batter is dismissed or a spell/innings ends, and enough temporal coverage. Keep observed-workload diagnostic models out of deployment selection.
2. Freeze row keys and as-of definitions. Create date-blocked historical summaries with a strict prior-date join for ordinary ability, pressure history, role, phase, tier, recency and opponent strength if used. Use a past-only prior and coverage flag for new players. Shift the summaries before joining labels. Run chronological reference fits for pressure coefficients, event frequencies, thresholds, wicket values and peer expectations. For initial warm-up blocks, use documented pre-existing rule priors or exclude them with counts. Never replace a missing dated dimension with full-history data.
3. Fit a simple pressure rule and a calibrated leverage candidate on comparable pre-ball states. For a leverage definition, use the dispersion of win-probability changes over possible events conditioned on earlier context, with correct resource transitions. Test 3/5 runs, legal and illegal deliveries, wicket plus runs, terminal states and competition-specific free hits. Use an empirically supported transition or document the omitted event classes and test sensitivity. Flag proxy transitions and low-support cells. Compare held-out match-weighted Brier, log loss, reliability bins and pressure-episode coverage by innings, phase and tier. Train calibration on an earlier block. A high-leverage situation can occur before the death overs.
4. Label a shared target on a common set of eligible rows. Keep runs above expectation and wicket residual contributions separate. For batting use observed bat runs minus expected bat runs, less wicket cost times the striker-dismissal residual. For bowling use expected charged runs minus actual charges, plus wicket cost times the credited-wicket residual. Use a validated past-only wicket cost or documented conservative constant. Choose a single primary reference for all ranking candidates. Test that altering a future fixture, a match's own outcome or its realized workload leaves all features available before that time unchanged. Assert stable keys under row reorder and cached/full rebuild.

Gate: dates and source hashes on all dependencies, no post-outcome feature, stable labels and feature schema, explicit IPL context and deployment unit, and falsifying tests for historical self-inclusion and future mutation. Leave 2026 marked previously inspected.

PASS -> round1_release_review/03_model_evidence_parity.md
FAIL -> repeat F02 for chronology, feature, calibration or target mismatches. Redirect event-accounting failures to round1_release_review/01_cricket_data.md.
BLOCKED -> STOP_BLOCKED with the support or time boundary preventing a credible target. Resume at round1_release_review/02_temporal_target.md when resolved.
```
